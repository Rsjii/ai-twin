## 3. Overall analytics architecture (high‑level design)

- **Layer 1 — Internal Event Store (already there)**
  - Postgres `Event` table = **canonical source**.
  - Server-side tracking from backend modules:
    - `auth`, `twin`, `chat`, `profile`, `invite`, etc.
  - Yehi data tumhare `admin-analytics` API endpoints use karte hain.

- **Layer 2 — Admin Analytics Service**
  - `backend/src/modules/analytics/*` jo:
    - Raw events ko aggregate karta hai (daily/weekly/monthly counts, breakdowns).
    - APIs deta hai:
      - `/api/admin/analytics/dashboard`
      - `/api/admin/analytics/time/:period`
      - `/api/admin/analytics/users`, `/user/:id/detailed`, etc.
  - Frontend `admin-analytics.ejs` isko charts / tables me dikhata hai (Chart.js, time filters, detailed views).

- **Layer 3 — External Analytics (PostHog / GA4)**
  - **PostHog**:
    - Event stream ka subset yaha push karo (same events but sanitized).
    - Use for: funnels, cohorts, retention, session replay, feature flags later.
  - **GA4 (optional)**:
    - Landing + marketing flows ke liye (traffic sources, campaigns).
    - Product events yaha minimal rakh sakte ho.

- **Identity & Privacy Layer**
  - Backend me tumhare paas `idTokenization.ts` hai → use this:
    - Internal `user.id` / `twin.id` / `chat.id` ko **public / hashed IDs** me map karo:
      - Internal DB + admin-analytics me safe usage.
      - External tools (PostHog/GA) ko **sirf hashed public IDs** bhejo.
  - No raw email, no raw message text external vendors ko.

### 4.3 Phase 4C – PostHog integration (recommended over pure GA)

**Goal:** Product analytics + investor dashboards + session replay.

#### 4.3.1 Tool choice: PostHog vs GA4 (short)

- **GA4:**
  - Pros:
    - Free, industry standard, accha for traffic/acquisition.
  - Cons:
    - Product analytics me limited; funnels/cohorts cumbersome.
    - Sampling / cardinality issues; data modeling thoda odd hai.
    - Self-host nahin; data EU/privacy tough.

- **PostHog:**
  - Pros:
    - Product-focused: events, funnels, cohorts, retention, session replay.
    - Open-source + self-host option → data control.
    - Good for **investor-facing dashboards** (growth, retention).
  - Cons:
    - Paid cloud for higher volume; learning curve.

**Meri recommendation:**
- **PostHog = primary product analytics tool.**
- GA4 agar chahiye to sirf marketing site ke liye later.

#### 4.3.2 Identity & privacy design

- Use `idTokenization.ts` or `publicId` pattern:
  - Internal DB: `user.id` (primary key)
  - External tools (PostHog/GA): `distinct_id = hashedUserId` (stable, reversible sirf tumhare backend ke liye).
- **Never send:**
  - email, raw messages, PII.
- **Send only:**
  - hashed id, coarse segments (country, plan, acquisition source), timestamps, event type + meta.

#### 4.3.3 Backend: server-side PostHog mirroring

Implementation outline:

- Install PostHog SDK in backend:
  - `npm install posthog-node`
- Configuration (env):
  - `POSTHOG_API_KEY`
  - `POSTHOG_HOST` (cloud or self-hosted).
- In tumhara central `logEvent` function:
  - After DB insert, asynchronously:
    - `posthog.capture({ distinctId, event, properties })`
- **Important:**
  - Use queue / fire-and-forget (no await in critical flow) to avoid latency.

Event mapping:

- Internal event `signup` → PostHog event `user_signup`
- `twin_created` → `twin_created`
- `chat_started` → `chat_started`
- `message_approved` → `message_approved`
- `profile_shared` → `profile_shared`
- `invite_sent` / `invite_accepted` similarly.

#### 4.3.4 Frontend: optional PostHog JS (for session replay)

- Add PostHog JS snippet on user-facing pages (not admin):
  - `frontend/src/views/*.ejs` me base layout ya header me:
    - Initialize PostHog with `distinct_id = hashedUserIdFromServer`.
  - Enable **session recording** cautiously:
    - Mask input fields, sensitive areas.
- Use JS tracking ke liye:
  - `posthog.capture('page_view', {...})` for key pages.
  - But major business events to already backend se aa rahe honge (more reliable).

#### 4.3.5 PostHog dashboards for investors

Create some standard dashboards:

- **Dashboard: “Traction & Growth”**
  - Cumulative signups
  - DAU, WAU, MAU line charts
  - Signup by source pie chart

- **Dashboard: “Activation Funnel”**
  - Funnel: `user_signup` → `twin_created` → `chat_started` → `message_approved`
  - Show conversion per step + time to convert.

- **Dashboard: “Retention & Stickiness”**
  - Cohort tables: retention by signup month.
  - Average sessions per week per user.

- **Dashboard: “Virality”**
  - Invites sent per active user.
  - Invite acceptance rate.
  - Profile shares vs new signups from profile.

- **Dashboard: “Product Usage Deep Dive”**
  - Chat length distribution
  - Twins per user distribution
  - Top public profiles.

## 5. Data governance / security (bahut important for investors)

- **ID masking:**
  - Everywhere outside backend (EJS, JS, PostHog, GA) use public/hashed IDs.
- **Content safety:**
  - Events me **message text** kabhi mat bhejo external tools ko.
  - Sirf counts, lengths, categories (e.g. `message_length_bucket`).
- **Access control:**
  - `/admin/analytics` + external dashboards sirf founders / limited people ko.
- **Consistency:**
  - Source of truth = Postgres + internal analytics.
  - PostHog/GA derived views hain; discrepancies pe DB ko trust karo.
