## 3. Final plan – kaise fix karna (ultra-detailed, step-by-step)

### Phase 1 – Core ID abstraction (use what you already have)

**Step 1.1: Standardize token usage**

- Resource types and tokens:

  - **User**
    - Internal: `user.id`
    - Public token: `tokenizeId(user.id, 'user')` → `user.publicId`

  - **Twin**
    - Internal: `twin.id`
    - Public handle: `twin.publicHandle` (already exists and used for SEO/URLs)
    - Token: `tokenizeId(twin.id, 'twin')` → `twin.publicId`

  - **Chat / PublicChat**
    - Internal: `chat.id`
    - Token: `tokenizeId(chat.id, 'chat')` → `chat.publicId` / `publicChatId`

- **Rule**:
  - **Public routes & HTML**:
    - Use `publicHandle` (for pretty URLs) **or** `publicId` (opaque token).
    - Never embed raw DB `id` in HTML, URL, localStorage, etc.
  - **APIs**:
    - Accept `publicId` in URL/body, use `detokenizeId` to map back to DB id server-side.
    - Return `publicId` fields in JSON; avoid raw `id` unless explicitly admin-only.

You already have:

```ts
sanitizeTwin(twin)  → { publicId, publicUserId, ... }
sanitizeChat(chat)  → { publicId, publicTwinId, publicUserId, ... }
sanitizeUser(user)  → { publicId, ... }
```

→ Plan is to **use these sanitized objects** consistently in controllers that power public/user UIs.

---

### Phase 2 – Public twin & public chat: fix twinId exposure

#### 2.1 Backend: introduce + use twin token in public chat APIs

- In `publicChatController.getUserPublicChats`:

Currently:

```ts
twin: {
  id: row.twinId,
  publicHandle: row.publicHandle,
  // ...
},
latestChat: {
  id: row.chat_id,
  // ...
}
```

**Change (conceptual)**:

```ts
import { tokenizeId } from '../../utils/idTokenization';

twin: {
  publicId: tokenizeId(row.twinId, 'twin'),
  publicHandle: row.publicHandle,
  // NO raw id
},
latestChat: {
  publicId: tokenizeId(row.chat_id, 'chat'),
  // NO raw id
}
```

- Ensure the **public chat list APIs** always return `publicId` instead of raw `twinId`/`chat_id`.

- Wherever there is a route like `/api/public-chat/twin/:twinId/...`:
  - Change param to `:twinToken`.
  - Inside controller: `const decoded = detokenizeId(twinToken)` → `actualTwinId`.

This matches how admin analytics already uses `detokenizeId`.

#### 2.2 Frontend: `public-chat.ejs` & `public-profile.ejs` – switch to tokens

- Instead of:

```ejs
let currentTwinId = '<%= twin.id %>';
// Used in URLs: /public-twin/chat/${currentTwinId}, /api/public-chat/twin/${currentTwinId}/...
```

Change to:

- Backend controller for these pages should pass a **tokenized twinId**, e.g.:

```ts
// when rendering public-chat/public-profile
const safeTwinId = tokenizeId(twin.id, 'twin');
res.render('public-chat', { twinPublicId: safeTwinId, twin /* without raw id in template if possible */ });
```

- In `public-chat.ejs` / `public-profile.ejs`:

```ejs
let currentTwinId = '<%= twinPublicId %>'; // token, not raw DB id

// URLs/APIs:
fetch(`/api/public-chat/twin/${currentTwinId}/chats?...`);
window.location.href = `/public-twin/chat/${currentTwinId}`;
// etc.
```

**Result:**

- User sees only opaque tokens in URL / HTML.
- Server alone knows how to map token → DB id (`detokenizeId`).

### Phase 4 – Chat IDs

For **user-private chat**, leaking `chat.id` is not terrible, but for a clean model:

- On backend, when returning chat lists, use `sanitizeChat(chat)` from `idTokenization.ts`:

```ts
// Instead of returning raw chat rows:
res.json({ chats: rows.map(chat => sanitizeChat(chat)) });
```

- In EJS:

```ejs
data-chat-id="${chat.publicId}"  // token instead of chat.id
```

- Any JS API calls that hit `/api/chat/:id/...` should be switched to `/api/chat/:chatToken/...` and use `detokenizeId(chatToken)` server-side.

For **public chat** (`PublicChat` / `PublicMessage`), same pattern: tokenise `chat.id` and use tokens in URLs and attributes.

---

### Phase 5 – Sanitization discipline in controllers

**Rule for controllers:**

- **Public / user-facing APIs** → always:

```ts
import { sanitizeUser, sanitizeTwin, sanitizeChat, sanitizeMessage, sanitizeEvent, sanitizeInvite } from '../utils/idTokenization';

const safeTwins = twinRows.map(sanitizeTwin);
res.json({ success: true, twins: safeTwins });
```

- Never send raw DB rows directly out of controllers, specially for:

  - `discover`
  - `public chat` APIs
  - social APIs (`/api/social/stats`, `/api/social/toggle-like` responses)
  - analytics APIs consumed by frontend.

Already discovered:

- `discoverController.ts` uses `tokenizeId` heavily → good.
- `adminAnalyticsController` already uses `detokenizeId` on inbound, and returns event break down & metrics (admin-only). For admin, you can keep raw IDs, or if you want uniformity, also sanitize.

### Phase 6 – Concrete rollout strategy

1. **Introduce / verify `publicId` fields in all relevant queries:**
   - Ensure `sanitize*` functions cover User/Twin/Chat/Message/Event/Invite (they already do in `idTokenization.ts`).
   - Start using them in controllers powering public/user UIs (discover, public chat, dashboard cards, analytics details).

2. **Switch public URLs & APIs to tokens:**
   - `/public-twin/chat/:twinId` → `:twinToken` + `detokenizeId`.
   - `/api/public-chat/twin/:twinId/...` → `:twinToken`.
   - `/analytics/details?type=...&twinId=` → token + detokenize.

3. **Patch EJS views:**
   - Replace `twin.id` with `twin.publicId` (or `twin.publicHandle` if route is handle-based).
   - Replace `data-chat-id="${chat.id}"` with `{chat.publicId}` for any new sanitized JSON.
   - For admin: optionally show both `publicId` and raw `id` in a debug-only tooltip.

4. **Hardening & validation:**
   - Centralise detokenization + auth checks:
     - After `detokenizeId`, always verify the requesting user is allowed to access that resource (ownership / visibility).
   - Add logging when `detokenizeId` fails or token type mismatch happens.

5. **Gradual deprecation of raw IDs in responses:**
   - Mark all places returning raw `id` as TODO.
   - For compatibility, you can for some time return **both** `{ id, publicId }` in private APIs, then eventually drop `id`.
